# Архитектура Generation Agent

HTTP-сервис хранит очередь в generation-data и запускает отдельный процесс Codex CLI
на задание. Backend владеет прикладными данными; агент не обращается к HH и не сохраняет
оценки в БД приложения. Входы и результаты разных заданий используют отдельные рабочие папки.

## Границы и повторы

POST сохраняет задание и ключ идемпотентности до запуска. Повтор того же ключа и входа
возвращает прежнее задание. Fingerprint включает вид задачи, нормализованный вход,
модель, reasoning и версию prompt. Другой вход или настройки с тем же ключом дают 409 KEY_CONFLICT.
После неопределённого исполнения автоматического повторного вызова модели нет.

Обычная очередь писем и помощников последовательна. Оценка вакансий, извлечение рынка
и прежний market-coverage разделяют общий настраиваемый лимит анализов. Резерв памяти
и приоритет обычной очереди сохраняют возможность подготовить письмо во время анализа.
Лимит 4 по умолчанию — политика проекта, а не заявленное ограничение провайдера.

Авторизация хранится в отдельном volume. GET /auth/status читает снимок; refresh, login,
старт сервиса и генерация при устаревшем снимке могут проверить действующий вход.
Отсутствие или наличие файла credentials само по себе не доказывает состояние аккаунта.

## Диагностика задержек

`GET /metrics` возвращает безопасные метрики сохранённых заданий. Фильтр
`GET /metrics?runId=<UUID>` выбирает один запуск параллельной оценки или анализа рынка backend.
Чтение не вызывает модель, auth refresh или повтор задания. Доступ ограничен
теми же локальными Host/Origin-проверками, что и остальные endpoints.

- `summary`: состояния и ошибки, число результатов оценки, полученных агентом, успешные и неудачные
  завершения за последнюю минуту, сообщённые CLI счётчики токенов.
  Получение результата агентом ещё не подтверждает запись оценки в БД backend.
- `latencyMs`: очередь, исполнение, CLI, полный срок и запись состояния running.
  `phasesMs`: `auth`, `prepare`, `cli`, `validate`, `rateLimitCheck`, `cleanup`.
  Для завершённых заданий считаются count/min/p50/p95/max/mean; отсутствующие
  замеры не превращаются в нули. p50/p95 — ближайший верхний ранг выборки.
  `activeAgesMs` и `queuedAgesMs` отдельно показывают возраст незавершённых заданий.
- `jobs`: до 200 записей, активные первыми. Сводка учитывает все совпавшие задания;
  `truncated` сообщает об ограничении подробностей. Для новой оценки известны
  `runId` и `batchIndex`; для `market-<runUUID>-extract-<index>-attempt-<attempt>` также
  передаются `runKind` и номер `attempt`. Пользовательский Idempotency-Key не публикуется.
  `evaluatedVacancies` считает ответы оценки, `extractedVacancies` — извлечение рынка.
  Это счётчики агента, а не подтверждение применения результата backend.
  Для сравнения прогонов передаются модель, reasoning, версии CLI/prompt и timeout.
- Живой `telemetry.stage` показывает текущий этап; таймеры продолжают идти
  даже при отсутствии вывода CLI. `resourceUsage` содержит текущий и пиковый
  замер памяти, `admission` — бюджет и вместимость на момент выдачи задания.
- `telemetry.cli`: запуск процесса, запись stdin, первый stdout/stderr,
  `thread.started`, `turn.started`, первый item/agent_message, завершение turn,
  выход процесса, код/сигнал выхода, объёмы потоков и длительность тишины.
  Отсутствующее событие имеет значение null, а не предполагаемое время.
- Фиксированные счётчики сообщений: retry/reconnect, rate limit, сеть,
  SQLite busy/locked, ресурсы и авторизация. Они учитываются в stderr и
  сообщениях JSONL error/turn.failed без сохранения исходного текста.

Тайминги событий означают момент их получения нашим процессом. `turn.started`
не доказывает принятие запроса сервером, а первый agent_message не равен
гарантированному времени первого токена. Диагностические счётчики — признаки
сообщений, а не доказательство причины ошибки или остатка квоты. Описание формата событий доступно в [официальной документации OpenAI](https://learn.chatgpt.com/docs/non-interactive-mode#make-output-machine-readable).

Живые метрики доступны также при обычном опросе задания. Терминальные тайминги
сохраняются вместе с заданием на прежний срок хранения; старые записи без них
остаются совместимыми. После перезапуска у прерванных заданий нет восстановленного
живого таймера. Строка `GenerationMetrics <JSON>` в логах содержит безопасную
сводку одного завершения. Prompts, ответы, raw stdout/stderr, credentials и thread ID
в метрики и эти строки не включаются. Сырые потоки обрабатываются
только в памяти с общим ограничением 2 МиБ; парсер метрик ограничивает
отдельную строку 64 КиБ и учитывает пропущенные строки счётчиком.

Для записей без инструментации отсутствующие тайминги возвращаются как null;
внутренние этапы завершившихся запусков задним числом не восстанавливаются.

## Хранение, ограничения и остановка

- `vacancy-relevance`, `market-extraction` и прежний `market-coverage` используют общую
  параллельную очередь: отдельный процесс Codex на каждую принятую пачку, с допуском
  по бюджету и доступной памяти. `GENERATION_MAX_CONCURRENT_ANALYSIS=4` ограничивает
  суммарное число процессов этих трёх видов. Если новой настройки нет, читается прежняя
  `GENERATION_MAX_CONCURRENT_RELEVANCE`; если нет обеих — 4. Диапазон 1–1000.
  Память может уменьшить допуск; остальные пачки остаются `queued`.
  Для каждого процесса используется своя временная рабочая папка.
- Письма, ответы на вопросы и решения задач обслуживает один последовательный worker,
  независимо от выполняемых анализов. `GENERATION_MAX_PENDING` ограничивает только
  эту обычную очередь: по умолчанию 20 незавершённых задач. Анализы в лимит не входят.
  Обычная очередь получает приоритет при допуске и не входит в потолок анализов.
  В `/health` поля `running`/`queued` показывают все задания,
  `runningAnalysis`/`queuedAnalysis` — все анализы, а
  `runningRelevance`/`queuedRelevance` — только оценку вакансий.
- Бюджет планировщика по умолчанию — `GENERATION_MEMORY_PERCENT=25` процентов памяти,
  доступной ОС или ограниченной контейнером. В Docker Desktop расчёт относится к памяти
  Linux-окружения Docker. Фиксированные `mem_limit: 1g` и `pids_limit: 128` убраны;
  Compose отключает собственный PID-лимит через `pids_limit: -1`.
- Из бюджета вычитается память Node (минимум 64 МиБ) и 64 МиБ для служебной работы.
  Перед новым запуском также сохраняется свободный запас для системы: максимум из
  10% доступного общего объёма и 128 МиБ. Задания резервируют свою расчётную память
  сразу при выдаче, до появления RSS процесса. Избыточные задания остаются `queued`.
- Начальная оценка одного исполнения — `GENERATION_JOB_MEMORY_MIB=128` МиБ.
  Это настраиваемая стартовая оценка. В Linux измеряется RSS и swap дерева процессов
  CLI; после успешного измеренного исполнения используется наибольший наблюдавшийся
  пик с коэффициентом 1,5 и минимумом 64 МиБ. Растущий расход учитывается сразу,
  а уменьшение стартовой оценки допускается только после успешного завершения.
  Замеры периодические и могут пропустить краткий пик; бюджет управляет выдачей задач,
  уже работающие процессы при изменении памяти принудительно не завершаются.
- Нативный запуск вне Linux использует стартовую оценку и данные доступной памяти ОС.
  Ошибка чтения `/proc` также сохраняет оценку. При отсутствии данных о памяти новые
  задания ожидают. Параметры проверяются при старте: доля 5–75%, оценка 64–16384 МиБ.
- Обычная очередь имеет приоритет при выдаче. При достаточном бюджете массовая оценка
  оставляет одно место для обычной очереди; машина с единственным доступным местом
  всё равно может выполнять анализ. Письма и помощники между собой остаются последовательными. Ошибка системных ресурсов возвращается как `RESOURCE_EXHAUSTED`.
- `/health.resources` содержит `budgetBytes`, `totalBytes`, `availableBytes`, `perJobBytes`,
  `observedPeakPerJobBytes`, `calibrated`, `capacity`, `availableSlots`, `availableRelevanceSlots`,
  `availableAnalysisSlots`, `activeReservations`, `maxConcurrentAnalysis`, `source` и `waitingReason`.
  Прежние `availableRelevanceSlots` и `maxConcurrentRelevance` остаются aliases общего лимита.
  `capacity` отражает расчёт по памяти, `availableAnalysisSlots` учитывает также потолок
  параллельности. Допустимый потолок — целое число 1–1000, по умолчанию 4.
  Причины ожидания: `MEMORY_UNKNOWN`, `BUDGET_BELOW_SINGLE_JOB`, `MEMORY_PRESSURE`,
  `INTERACTIVE_RESERVE` и `CONCURRENCY_LIMIT`.
  Для чтения доступной памяти используются [API Node.js](https://nodejs.org/docs/latest-v24.x/api/process.html#processavailablememory).
- Задачи в отдельном volume `generation-data`, JSON записывается через временный файл и rename.
- Входные тексты сохраняются для очереди, но удаляются из задачи после завершения.
  Результат/замеры удаляются через 7 дней (настройка retention, очистка во время работы сервиса).
- Сырые JSONL/stderr не сохраняются и не попадают в HTTP. Итоговый временный файл
  удаляется после обработки; `--ephemeral` отключает сохранение rollout-сессии.
  Это не обещание отсутствия внутренних служебных файлов самого CLI в auth-volume.
- Остановка прерывает активный CLI; процессная группа получает SIGTERM, затем SIGKILL.
  После аварийного перезапуска старые `running` становятся `failed/INTERRUPTED`,
  а ещё не начатые `queued` продолжаются. Замеры оборванного запуска могут быть `null`.
- Ошибка сохранения результата останавливает worker, чтобы не вызвать модель повторно.
- Не запускай несколько экземпляров сервиса на одном data-volume.
- Контейнер работает не от root, без исходников/БД/Chrome-профиля/Docker socket.
  Передача данных модели идёт через stdin, рабочая папка временная, sandbox read-only,
  shell и web search отключены. Не включён bypass из прототипа.
- HTTP без токена: порт публикуется **только на 127.0.0.1**, CORS отсутствует,
  разрешены localhost, `host.docker.internal` и имя сервиса `generation-agent` для backend-контейнера, браузерный Origin отклоняется. Используй Postman Desktop/curl; веб-клиент может
  блокироваться. Это не защита от других локальных процессов/пользователей компьютера.

```powershell
docker compose logs -f generation-agent
docker compose stop
```

`docker compose down` сохраняет данные и вход. Не добавляй `-v`, если не хочешь
потерять авторизацию и результаты. Другие репозитории/контейнеры не изменяются.
